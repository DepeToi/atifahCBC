# 架构设计工作流

## 本项目的既定约束（不要重新发明）

- 一服务一库；服务间只走 HTTP/Feign（已有 openfeign + loadbalancer 依赖），不做跨库 JOIN。
- 网关统一鉴权与路由；新接口默认需要令牌，白名单只能是认证入口与健康/指标端点。
- 配置分两层：各服务本地 `application.yml` 放端口/应用名/库地址，共享项放 Nacos `common-application.yaml`。
- 已有 Redis/Redisson、RocketMQ、Sentinel；引入它们要说明为什么现有能力不够。
- Java 21 虚拟线程已开启（`spring.threads.virtual.enabled`），阻塞式 IO 不是首要问题。

## 设计取舍的默认判断

| 场景 | 默认选择 | 什么时候才升级 |
| --- | --- | --- |
| 读多写少的展示数据 | 直接查库 + 索引 | 热点且 QPS 高才加 Redis，并写清 key/TTL/失效策略 |
| 跨服务通知 | 同步 Feign（可接受失败即降级） | 要求最终一致或削峰时才用 RocketMQ，并定义消费幂等与死信 |
| 强一致写 | 单库事务 + 唯一索引 | 跨服务强一致才考虑 Seata（当前仅可选未接入） |
| 分页查询 | MyBatis-Plus 分页 + 覆盖索引 | 深分页才改游标 |
| 定时统计 | stats-service 内调度 | 数据量大再走离线任务 |

任何“引入新中间件/新服务”的方案，必须给出：运维成本、失败模式、回滚方式，以及不做会怎样。

## 步骤

1. 取证：相关代码、配置、已有迁移，标注 `文件:行号`。
2. 至少给两个方案（最小改动 / 目标架构），按影响面、数据变更、风险、工作量对比。
3. 选定方案补齐：契约、表结构与迁移、事务与并发、失败重试、性能容量、安全、可观测、发布与回滚、测试策略。
4. 落盘 ADR 到 `docs/adr/NNNN-<slug>.md`（目录不存在则创建），契约到 `docs/contracts/api/<service>.md`。
5. 回复先给结论，再给对比表，最后任务包。

## 反模式

- 为单个需求新建服务或新表而不先看能否复用。
- 用 MQ 解决本可以同步解决的问题，却不定义消费失败怎么办。
- 在事务里做远程调用。
- 设计里只写“正常流程”，不写失败、超时、重复请求。
