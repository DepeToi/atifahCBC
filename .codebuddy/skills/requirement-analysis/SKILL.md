# 需求分析工作流

## 判断依据

- 当前只有 `auth-service` 具备完整能力，其余服务是骨架；需求落到骨架服务意味着“从零建垂直切片”，工作量与风险要如实说明。
- 需求落在管理端时，注意 `admin-service` 还没有 BFF 接口，前端也只是静态骨架——不要承诺“改个页面就行”。

## 步骤

1. **读现状**：`docs/repo-status.md` + 目标服务的 `controller/`/`mapper/`/`db/migration/` + 网关路由。
2. **定位归属**：哪个服务、哪个库、是否跨服务。一个需求横跨两个服务时，先指出边界问题。
3. **写验收标准**：用“给定 … 当 … 则 …”，必须包含：正常路径、参数非法、未认证/越权、重复提交、空结果、边界值。每条都要能被测试或 curl 验证。
4. **列影响面**：接口（新增/修改）、表与迁移版本、网关路由与白名单、Nacos 配置、compose、前端页面与类型、README。
5. **拆任务包**：每项包含“允许修改路径”和“完成判据”，粒度以一次提交能完成为准；把契约变更单独成一项。
6. **列风险与待确认**：不确定的写问题，不写假设。

## 输出骨架

`目标 / 非目标 → 场景 → 验收标准 → 影响面表 → 任务包 → 风险 → 待确认`

## 质量自检

- 每条验收标准都能对应到具体接口或表字段吗？
- 是否遗漏“失败与重试”“并发与幂等”“数据保留/清理”？
- 是否把“未来可能”混进本期？
- 所有“已存在”的判断是否附了 `文件:行号`？
