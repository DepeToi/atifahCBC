# 缺陷修复：$ARGUMENTS

## 1. 复现

- 明确触发条件：接口/页面/命令、输入、期望与实际。
- 能本地复现就复现（单测、`curl`、日志）；不能复现就说明缺什么（环境、数据、Nacos、中间件）。
- 找证据：相关日志行、异常栈、`traceId`、数据库记录。

## 2. 定位根因

- 沿调用链读代码：controller → service → mapper/远程调用，标 `文件:行号`。
- 区分“根因”和“暴露点”：空指针只是症状，空值从哪来才是根因。
- 常见根因类型：参数未校验、事务边界错误（远程调用在事务内）、唯一键/幂等缺失、Nacos 配置缺失、网关路由/白名单不匹配、时间与时区、字符集。

## 3. 先写失败用例

在 `src/test/java` 补一个能稳定失败的用例（覆盖真实失败路径，不是复制成功路径）。跑一次确认它失败。

## 4. 修复

- 最小改动，只修根因；不顺手重构无关代码。
- 不吞异常、不降级校验、不删测试、不加 `catch (Exception ignored)`。
- 涉及契约/表结构时按 `/project:api-change` 处理，单独成 PR。

## 5. 验证与报告

```bash
mvn -o test -pl <模块> -am
mvn -o test          # 改了 common-* 时
```

报告：现象 → 根因（`文件:行号`）→ 修复方式 → 用例前后对比 → 风险与影响面 → 是否需回归其他服务。
