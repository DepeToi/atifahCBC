# 代码评审：$ARGUMENTS

只读。不要修改任何文件。

## 1. 确定范围

1. 先跑 `git rev-parse --is-inside-work-tree`：
   - 成功：`git status --short` + `git diff`（必要时 `git diff --staged`）取改动。
   - 失败（当前仓库即如此）：告知用户“无 git 基线”，请其指定路径，或按最近修改的文件（按修改时间）列出候选。
2. 范围限定在用户指定路径；不要顺手评审无关模块。

## 2. 评审清单（按本项目）

- **返回与错误**：是否统一 `Result`；是否抛 `BusinessException(ErrorCode)`；错误码是否新增在枚举而非裸数字。
- **入参校验**：DTO 是否 record + `jakarta.validation`；是否漏 `@Valid`；提示是否中文。
- **事务与远程调用**：`@Transactional` 内是否有 Redis/MQ/Feign；事务范围是否过大。
- **幂等与并发**：写接口是否处理 `Idempotency-Key`；唯一性是否靠唯一索引而非先查后插；重复请求是否返回一致结果。
- **数据库**：迁移是否新增未改历史；命名/索引/注释/时间列是否合规；是否向前兼容。
- **安全**：日志是否泄露手机号/密码/令牌；是否越权（管理端 role 校验）；SQL 是否参数化。
- **网关与配置**：新接口是否需要路由/白名单；配置项是否有默认值、是否同步 Nacos/compose。
- **测试**：是否覆盖失败与边界；是否删/弱化既有断言；是否依赖真实中间件。
- **可读性**：命名、分层、重复代码、过度抽象。

## 3. 输出

按严重级别分组，每条给 `文件:行号`、问题、影响、修复建议：

- **P0**：会导致数据错误、越权、密钥泄露、线上不可用 → 必须改
- **P1**：违反项目硬约定、缺关键测试、明显并发/事务缺陷 → 建议本次改
- **P2**：可读性、命名、注释、可选优化

最后给一段总评（能否合并 + 必改项数量）。没有问题就说没有，不要凑数；不确定的标“待确认”并说明依据。
