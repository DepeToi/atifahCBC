# 契约变更：$ARGUMENTS

契约变更必须单独成 PR。先产出影响清单，再动代码。

## 1. 现状

- 找到现有契约实现：controller、DTO/VO、错误码、网关路由、前端调用点、契约文档（`docs/contracts/` 可能尚不存在）。
- 记录现有请求/响应示例（从代码推断，不要编造字段）。

## 2. 影响清单（必填）

| 维度 | 影响 | 处理 |
| --- | --- | --- |
| 路径/方法 | | 网关 routes、白名单、README |
| 请求字段 | 新增/必填化/删除 | DTO、校验、前端表单、测试 |
| 响应字段 | 新增/改类型/删 | VO、前端 types、表格列 |
| 错误码 | 新增/语义变化 | `ErrorCode`、`GlobalExceptionHandler`、提示文案 |
| 数据 | 表/索引/迁移 | 新 `V{n}`、向前兼容 |
| 兼容性 | 旧客户端是否可用 | 双写/默认值/版本化 |

## 3. 判定

- 向后兼容（只加可选字段/新接口）：可直接做，仍需同步文档与前端类型。
- 破坏性（删字段、必填化、改语义、改状态码）：默认拒绝，改为“新增字段 + 双写 + 下线旧字段”三步，并写清下线时间点。
- 改路径：同时更新网关、README、前端 baseURL 调用、契约文档；考虑保留旧路径一段时间。

## 4. 实施与验证

1. 按 `/project:feature` 的顺序改代码（DTO→迁移→service→controller→测试）。
2. 更新契约文档与 README（若涉及路由/端口）。
3. 跑 `mvn -o test -pl <模块> -am`；前端改动补 `npm run build`。
4. 回复里给出“契约 diff + 兼容性结论 + 迁移/回滚方式 + 需要谁配合（前端/运维）”。
