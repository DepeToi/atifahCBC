# 需求分析：$ARGUMENTS

按下面顺序做，**先取证再下结论**，全程不改代码。

## 1. 取证

1. 读 `docs/repo-status.md` 确认当前真实能力；必要时抽查相关模块的 `controller/`、`mapper/`、`db/migration/`。
2. Grep 现有实现（`Result`、`ErrorCode`、网关路由、相关实体），确认需求是否已有部分能力。
3. 明确需求落在哪个服务/模块，是否跨越服务边界。

## 2. 澄清

信息不足时不要臆测。列出**必须确认的问题**（不超过 5 个），必要时用 AskUserQuestion 只问最关键的一两个，其余写进“待确认”。

典型待确认点：谁能调用（C 端/管理端）、幂等要求、分页与排序、数据保留期、失败重试、是否需要离线/实时、是否有既有契约必须兼容。

## 3. 输出（直接回复，不落盘）

```markdown
## 目标与非目标
- 目标：
- 非目标（本迭代明确不做）：

## 用户与场景
- 角色 / 触发场景 / 期望结果

## 验收标准（可测）
1. 给定…当…则…（含错误分支与边界）

## 影响面
| 层 | 位置 | 变更 |
| 服务/模块 | | |
| 接口 | | |
| 数据 | 表/迁移版本 | |
| 网关 | 路由/白名单 | |
| 前端 | 页面/接口 | |
| 配置 | Nacos/compose | |

## 约束与风险
- 兼容性、并发、性能、安全、上线顺序

## 任务包（每项含“允许修改路径”）
1. 任务名 — 改动路径 — 完成判据

## 待确认问题
```

## 规则

- 不把“未来可能要做”混进本期范围；非目标要写清。
- 涉及新表/改表时，先判断能否复用现有表，避免为单个需求造表。
- 需求需要新服务时，同时列出 `/project:design` 必须回答的问题（拆库、调用链、失败处理）。
- 结论里凡是“已存在”的判断，附 `文件:行号`。
