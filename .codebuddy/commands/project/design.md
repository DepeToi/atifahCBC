# 技术方案：$ARGUMENTS

先看代码，再谈方案。禁止在未确认现状的情况下给“新建一套”的方案。

## 1. 现状取证

- 相关服务的 `application.yml`、pom、已有 controller/service、迁移脚本。
- 网关路由、Nacos 共享配置、compose 编排里与该主题相关的部分。
- 结论标注 `文件:行号`；不确定的写“待确认”，不要编。

## 2. 方案对比（至少两个）

每个方案写：核心做法、影响模块、数据变更、优点、代价、风险。至少包含“最小改动方案”和“目标架构方案”。

选型维度按本项目实际：一服务一库、Nacos 配置热更新、网关统一鉴权、MyBatis-Plus、Redis/Redisson、RocketMQ 可用、容器化部署、团队 Java 21 虚拟线程。

## 3. 选定方案要回答

1. 服务边界：放哪个服务，为什么不是别的服务（避免跨库）
2. 接口契约：方法、路径、请求/响应字段、错误码（复用 `ErrorCode`）、幂等键
3. 数据：表结构、索引、迁移文件 `V{n}`、是否需要回填、向前兼容策略
4. 一致性与并发：事务边界、远程调用是否在事务内、唯一约束兜底、重复提交处理
5. 失败与重试：超时、降级、死信/补偿，MQ 是否必需
6. 性能与容量：预计 QPS、索引命中、缓存键与 TTL、分页上限
7. 安全：鉴权、越权、敏感字段、日志脱敏
8. 可观测：日志字段、指标、健康检查
9. 发布与回滚：上线顺序、开关、灰度、回滚步骤
10. 测试策略：单测覆盖的成功/失败/并发路径

## 4. 落盘

- ADR：`docs/adr/NNNN-<slug>.md`（`docs/adr` 不存在就创建），编号四位递增，包含背景/决策/备选/后果。
- 契约：`docs/contracts/api/<service>.md`（如涉及接口变更）。
- 若结论是“不改代码”，也写清依据。

## 5. 回复格式

先给 3-6 行结论（选了什么、为什么、影响哪些模块），再给对比表，最后给任务包（每项含允许修改路径）。方案确认前不要动手实现。
